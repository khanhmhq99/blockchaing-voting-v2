# MACI decisions and open gates

## 2026-10-15 owner-directed prototype continuation

The owner accepted continuing M2–M7 implementation while M0 independent setup, contributor, dependency and production architecture reviews remain deferred. Their results must remain unknown/open, not passed. This changes the implementation sequencing for a synthetic thesis prototype; it does not establish suitability for real elections or automatically authorize BSC deployment.

M2 uses a minimal new registration policy/entry contract because upstream MACI v3.0.0 `signUp` passes `msg.sender` and policy data, but does not pass the MACI public key to its policy. The registration contract checks an issuer EIP-712 signature over a random one-use ticket, public key, deadline, chain and verifying contract, then calls MACI itself. Its `enforce` method accepts only the MACI callback for the pending exact evidence, so a sponsor cannot substitute a key. The issuer database must enforce one ticket per authenticated eligible account per MACI deployment. The issuer sees the account-to-ticket join and can correlate public registration; no anonymity against the issuer is claimed. MACI's poll membership proof and nullifier remain the join uniqueness enforcement, with a sponsor-independent poll policy. Loss after on-chain registration is not recoverable without a new election/protocol; the client must retain an encrypted backup.

The current Desktop Web bundle uses pinned MACI v3.0.0 SDK/domain/crypto packages and official joining artifacts. Upstream SDK browser exports pull in unused Node `fs`/`os` modules; Next 16 Turbopack aliases those to an empty module in browser builds. MACI v3's `crypto.randomBytes` adapter uses the browser Web Crypto CSPRNG. The voter key, signing and encryption stay in browser code; the browser backup uses PBKDF2-SHA256/AES-256-GCM with a user-held passphrase. This bundle compiled, but key generation, proof generation and restoration still need a real browser runtime probe against a local poll. Dependency advisories remain deferred review, not accepted cryptographic assurance.

Registration sponsorship uses an authenticated issuer-side endpoint and a dedicated EVM signer. Poll joining and encrypted-message submission use cookie-free endpoints and separate funded signers. Database tables have no join foreign key to `AppUser` for anonymous submissions; the issuer, relay and database still run under one API operator, which can correlate timing. Raw signed transactions are stored for idempotent rebroadcast and receipt reconciliation. A confirmed encrypted message means chain inclusion only; the coordinator proof and tally publication paths are separate. The explicit coordinator CLI excludes private `circuitInputs` from the public evidence files. The audit ingestion endpoint checks canonical chain logs, successful submitted proof transactions, on-chain verifier keys/proofs, and the tally commitment before setting `VERIFIED`. Its implementation has not yet been exercised with a migrated local database.
