# ADR 0009: MVP 3 encrypted-ballot proof composition (proposed)

Status: **Proposed; architecture decision required**. Date: 2026-10-13. The owner authorized a local research adaptation and conditional development/testnet deployment once security gates pass. This ADR does not supersede ADRs 0003–0006; the deployment condition is not yet met.

## Context

MVP 3 must accept a ballot only when a frozen-root anonymous credential and an exactly-one encrypted ballot are both proved on chain. It must bind the accepted ciphertext, election key, manifest and process parameters to the proof and nullifier, preserve accepted public evidence, and support aggregate-only normal decryption with checked evidence. The single election-key holder remains able to decrypt individual ciphertexts. [Local feasibility evidence](../../mvp3/FEASIBILITY_EVIDENCE.md) shows real Semaphore and DAVINCI proofs can be verified in one Hardhat transaction, but the wrapper accepts an unchanged proof with a mutated ciphertext record because it does not authenticate DAVINCI's public hash against those bytes.

## Proposed decision

Prefer **two independent, versioned proof verifiers**: Semaphore v4 for membership and nullifier, and a reviewed exact-one BabyJubJub ElGamal ballot circuit for encryption validity. The contract must derive the scope from protocol version, chain ID, its address and election ID; enforce one frozen root; validate canonical ciphertext/key/manifest fields against the ballot proof's public statement; bind that statement to the Semaphore message; and consume the nullifier only in the same successful transaction that records the accepted ciphertext. An exact cross-language encoding and digest specification with mutation vectors is required. Never use caller-supplied `inputs_hash` as a substitute for recomputing or otherwise proving the accepted record binding.

The original DAVINCI proof exposes only three public signals, so a contract-only fix would require an exact, reviewed on-chain Poseidon(16) implementation. The installed generator supports at most eight inputs. The minimum demonstrated alternative is to expose the already constrained process ID, mode, key, ciphertexts and weight as additional **public signals**; the contract constructs all signals from the accepted record and frozen election state, and the circuit checks the final `inputs_hash` against them. No caller-controlled hash is trusted. This changes the Groth16 public input count and requires new circuit/proving/verifying artifacts and a new setup. It does not change ElGamal. [Research patch, contract and measured local probe](../../mvp3/FEASIBILITY_EVIDENCE.md) demonstrate this form of composition on Hardhat, including accepted ciphertext recording and negative cases. They do not approve deployment.

The circuit does not directly hash the candidate-order manifest, chain or contract address. The research contract freezes a canonical 128-byte manifest containing protocol version, election ID and two ordered candidate IDs, and derives process ID and Semaphore scope from its digest, chain ID and its own address using explicit field rejection sampling; it fixes the exact-one two-candidate mode and election public key. A focused probe discovered the upstream circuit allowed nonzero inactive plaintext and unverified padded ciphertext. The final [two-file patch](../../../research/mvp3/ballot-public-signals.patch) forces inactive plaintext zero and authenticates all 16 ciphertexts; only the two active fields enter tally. See [ballot specification](../../mvp3/BALLOT_SPECIFICATION.md). Before adoption, establish the DAVINCI source license, independent circuit/security review, phase-two ceremony provenance, artifact distribution, mobile browser bounds and BSC EVM compatibility. Specify a compatible reviewed aggregate-decryption proof and validate it against the accepted-set aggregate. If DAVINCI cannot satisfy these conditions, evaluate another reviewed circuit with equivalent public inputs. A unified circuit is a fallback only after its new circuit, trusted setup, audit and measurements exist.

## Alternatives and consequences

| Alternative | Consequence |
| --- | --- |
| Adopt the current DAVINCI + Semaphore wrapper | Rejected. An attacker can pair a valid proof with different ciphertext/key/manifest bytes. It would violate ADR 0003 on-chain ballot-validity enforcement. |
| Trust a backend ballot-validity filter or sequencer before an eligibility-only contract | Rejected without an explicit change to security requirements. The chain could accept altered or invalid ballots when that party fails or colludes. The database is a projection, not ballot authority. |
| Build one new unified circuit now | Deferred. Could reduce verifier calls, but creates a new unaudited circuit and setup with greater research and maintenance burden. |
| Use ElectionGuard specification/TypeScript subset as a drop-in EVM verifier | Deferred. The subset lacks ballot verification and decryption; curve/proof/serialization parity with the contract is unproven. |
| Separate reviewed proofs with authenticated shared public statement | Preferred research direction and locally demonstrated after public-input and padded-field circuit revision. Keeps claims legible, at the cost of new setup/verifier, 2,948-byte calldata and 1,053,309 local gas for the two-candidate probe. Review and remaining gates still prevent deployment. |

## Acceptance before status can become accepted

1. Choose exact licensed/reviewed source revisions, cryptographic parameters, artifact hashes and reproducible setup provenance; record dependency advisories and BSC target fork support.
2. Define canonical field encodings, ciphertext point validation, candidate and manifest bounds, key binding, hash domain and public record bytes. Reject malformed, noncanonical or altered record fields in the actual contract.
3. Run a complete local contract acceptance probe for valid and invalid selection, missing/multiple selection, wrong root/scope/election, altered ciphertext/key/manifest/proofs, and duplicate/replayed nullifiers. Measure full calldata, gas, browser proving and memory.
4. Demonstrate aggregation over the exact accepted ciphertexts, checked aggregate-decryption evidence and public reconstruction. Document the single-holder and timing-correlation limitations.

The 2026-10-13 local result satisfies a research encoding and the contract mutation/gas portions of item 3. One Edge headless proof passed in 5,559.60 ms, with 320,951,881-byte JS heap after proof; this is no mobile bound. Two accepted ballots were aggregated and internally decrypted to `[1,1]`, but there is no public decryption proof. On 2026-10-14 the owner workstation made one phase-two contribution; `ballot_0001.zkey` passed verification against the pinned R1CS and ptau. That owner-only snapshot is superseded by the 2026-10-14 ceremony continuation: the returned `0002` and precommitted drand beacon `#3` both passed `snarkjs zkey verify` against the pinned R1CS/ptau, and the final-key local contract and one Edge headless proof passed. Independent setup is still **unconfirmed** because the second contributor provided only the zkey, without separately computed hashes or an attestation that they controlled private entropy on their own device. Phase-one transcript validation also remains pending. Source license/audit review, target BSC execution and item 4 also remain unmet. Neither the original `0000`, owner-only `0001`, nor final beacon key may be deployed as an election verifier while independent provenance and the other acceptance gates remain open. The owner's conditional testnet deployment and `.env` update authorization therefore remain unused. Existing private key values were not inspected. See [ceremony](../../mvp3/TRUSTED_SETUP.md), [tally](../../mvp3/TALLY_VERIFICATION.md), [browser](../../mvp3/BROWSER_BENCHMARK.md) and [final local evidence](../../mvp3/FEASIBILITY_EVIDENCE.md).

Until then the feasibility gate stays blocked and product-facing Checkpoints 1–7 must not begin.

The 2026-10-14 [source-rights and focused circuit inspection](../../mvp3/SOURCE_AND_CIRCUIT_REVIEW.md) found no explicit license for the pinned DAVINCI revision and no independent audit of this modification. The `.sym`/vkey mapping confirmed 72 public signals; the final-key contract probe rejected altered padded ciphertext and reversed candidate order. `circom --inspect` reported a `MaskGenerator` assertion absent from R1CS. No exploit was demonstrated under this contract's fixed two-candidate mode, but an independent reviewer must assess the warning and the full constraint system. Neither rights nor audit acceptance is implied by the local probe. A source/constraint correction would require new R1CS, WASM, setup contributions, beacon, verifier and final-artifact probes; mere license clarification would not.
