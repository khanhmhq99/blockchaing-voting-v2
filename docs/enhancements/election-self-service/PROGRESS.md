## Checkpoint 1 — data model and APIs

Added `MaciParticipationRequest` and `MaciDeploymentJob` plus unique request/idempotency keys, review timestamps, admin attribution and job diagnostics. Added a deployment instance marker to elections and anonymous projections so repeated chain-31337 addresses do not merge current and historic counts. Migrations: `202610240001_election_self_service` and `202610240002_local_chain_instances`. The second migration replaces three sets of uniqueness/index keys; its compatibility impact is recorded in ADR 0012. Both migrations were applied **only** to the isolated `mvp4_local` PostgreSQL fixture with verified TLS and `psql -X -q -v ON_ERROR_STOP=1 -1`: exit 0 each. The first attempt at migration 2 exited 1 on a PostgreSQL index-name truncation collision; the transaction rolled back, index names were shortened, and the successful retry exited 0. An early local-only case-normalization repair failed under the old unique index (exit 1); after migration 2, a scoped repair of one new synthetic row returned `UPDATE 1`. No historical row was changed by that repair.

Voters can request and inspect only their own participation. The backend validates authentication, account role/state, active chain binding and a cutoff before poll start. Admin review requires `PENDING`, checks the voter remains active, atomically changes request status and creates existing `MaciEligibility` only on approval. Serializable transaction conflicts return 409. The legacy username-assignment API is retained only for `legacy` elections and is forbidden for new self-service elections. Credential issuance and sponsored registration also enforce the cutoff using the later of chain and wall time.

## Checkpoint 2 — automated local deployment

`MaciDeploymentService` persists an intent and UUID idempotency key, claims one job through a database advisory transaction, starts the pinned local deployment script in a server child process and records checkpoint progress. It permits only chain 31337, uses server-side separated keys and never returns or logs them. It calls the existing pre-election candidate-anchor script, validates receipts/confirmations, contract code hashes, MACI issuer/policy/poll bindings and poll timing before persisting the election. The public canonical configuration is saved with the job and published automatically after audit verification. A claimed job with uncertain submission becomes `RECONCILIATION_REQUIRED`; it is not redeployed automatically. Startup and status polling can finish reconciliation from complete evidence. Unresolved jobs block later automatic claims.

The first new job `0d2be675-f753-47a3-b76a-8aa993903ec4` reached `RECONCILIATION_REQUIRED` during implementation because a typed parser stripped candidate IDs before recomputing the anchor hash. The parser was corrected, and the same deployed job reconciled to `READY` after API restart, without a second deployment. Its deployment and anchor files remain under ignored `research/mvp3/maci/probe-output/deployments/<jobId>/`. A second job `8b541b23-b6bf-42af-9d37-5c84fc6aeb3b` passed simultaneous create-key replay, and a third election was created through the browser form. Historical deployment files were not overwritten.

## Checkpoints 3–5 — admin, voter, lifecycle and monitoring

The admin creation form now has title, dynamic candidate fields, start and end times with displayed browser timezone; technical addresses are read-only after creation. It polls job progress and resumes the latest job after reload. A dedicated request table offers approval/rejection; manual username entry is absent from the new UI. Advanced operations retain explicit coordinator evidence publication. The voter page displays participation states, polls for review changes, and gates the existing client-held credential/backup/registration/join/vote journey. Join and encrypted-message status now poll until confirmed; an already-joined credential can rediscover its state index.

GET election list derives `REGISTRATION`, `OPEN` and `CLOSED` from verified current chain time; it never derives `VERIFIED` from time. The monitor retains a 15-second refresh, reports approval and projection counts separately from chain processing/tally counters, shows deployment/chain health, and suppresses projected join/message counts when the current deployment is invalid. Historical election `4b820fd9-cf18-47e2-ba1f-820a65a3d7d3` returned `INVALID`/`MACI_POLL_MISMATCH` on the new Hardhat chain; its old join/message counts were returned as `null` in the final code. The current election returned `AVAILABLE`. Confirmed included commands are a projection of submitted commands, not an exhaustive count of all `PublishMessage` events or counted votes. The public manifest contained three `PublishMessage` events, including a protocol initialization event at deployment block 17; the API had two confirmed user-command projections. An additional direct RPC event-count metric was removed because its live verification could not be completed after local services stopped.

## Current limitations and exact continuation point
