# MVP 2 gasless paired benchmark

Observed 2026-10-12. **Local EVM measurements with simulated voter interactions and explicit memory persistence.** These are exploratory single-run comparisons, not public-chain capacity, human MetaMask latency, production availability or live Supabase performance. No real cryptocurrency was spent.

Primary run: [comparison JSON](../../benchmarks/results/mvp2-paired-c173a3fe-bb01-467a-a741-dc6b1bed743c/comparison.json), [source hashes](../../benchmarks/results/mvp2-paired-c173a3fe-bb01-467a-a741-dc6b1bed743c/source-hashes.json), [driver snapshot](../../benchmarks/results/mvp2-paired-c173a3fe-bb01-467a-a741-dc6b1bed743c/benchmark-driver.ts). Each mode/size subdirectory contains manifest, raw transaction-attempts JSONL, logical-submissions JSONL and contract source. Complete API/helper/shared/contract/compiler input source and lockfile snapshots accompany the run. Starting Git revision is `e0c2ad1934ffbe38260106ce46cbcdaa7f22f982`; the working tree is dirty. Source hashes identify the actual uncommitted benchmark implementation.

The earlier [development measurement](../../benchmarks/results/mvp2-paired-25f4f786-e36e-4d33-a0a3-2061fc02f1c7/comparison.json) is retained but excluded from the primary table: it precedes stored-transaction validation hardening, queue-timing refinement and complete source snapshot capture. Its confirmation field included the admission-to-poll interval and is not comparable to the refined field below. Neither run overwrites the [original MVP 1 baseline](mvp-1-baseline.md).

## Controlled workload and differences

Both modes deploy a fresh contract on a fresh Hardhat chain 31337 on loopback, use two candidates, alternating selections, the same deterministic synthetic voter derivation, one sequential arrival after each confirmed receipt, the same eligible population, 200-wallet authorization batches and one-block confirmation. Node 24.21.0, npm 11.19.0, Windows/CPU/RAM, compiler/optimizer settings, first/last block hashes and raw checksums are recorded in every manifest. No warmup or independent statistical repetitions; no confidence interval is justified.

MVP 1 uses the unchanged BasicVoting contract, Paris target and funded voter transactions. MVP 2 uses GaslessVoting, Cancun target (required by pinned OpenZeppelin cryptography), a dedicated funded relayer and zero-balance voters. Signatures are generated by isolated deterministic development accounts, never MetaMask popups; no private keys are persisted. API signature verification, chain checks, simulation, gas estimation, durable-state orchestration and HTTP polling are included in MVP 2 E2E time. Direct baseline transactions do not go through the API. The database double serializes transactions and copies state for rollback; this artificial cost grows with history and cannot represent Supabase query/transaction latency. These differences prevent attributing all timing changes solely to EIP-712.

Every accepted vote is checked against receipt success, sender, balance deltas and the canonical VoteCast set. Relayer balance decrease must equal the sum of sponsored fees. Raw gas and fee values are exact decimal strings; averages below are derived statistics. Deployment/funding are excluded. Creation/candidate registration/authorization/freeze/finalization gas and fees are recorded separately as `setup` in manifests. Compute/RPC/storage monetary costs, public-chain finality and human signing time are **not measured**.

## MVP 2 timing breakdown

All values below are means in milliseconds.

| Voters | Synthetic signing | API validation | Queue wait | Broadcast RPC | Confirmation observation | E2E | Drained votes/s |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 0.854 | 21.003 | 1.900 | 5.516 | 7.600 | 88.185 | 11.120 |
| 100 | 0.686 | 16.514 | 1.720 | 4.486 | 6.130 | 72.110 | 13.620 |
| 1,000 | 0.683 | 15.960 | 5.894 | 4.553 | 10.561 | 98.718 | 10.004 |

Queue wait is admission commit to worker claim, excluding worker revalidation/preparation. Broadcast RPC is send duration, excluding local signing and database preparation. Confirmation observation begins after broadcast acknowledgement and ends when the backend verifies a canonical receipt/depth. MVP 2 uses server Date timestamps with millisecond resolution; MVP 1 uses driver performance.now after the transaction hash response. Local automining means inclusion can precede broadcast acknowledgement, so these intervals are receipt observation delays, not physical block production times. Neither is settlement finality. The components do not sum to E2E: wallet/balance reads, HTTP transit, repeated verification, estimation, signing, persistence and polling also contribute. Durations are encoded as integer nanosecond strings derived from measured milliseconds; this does not imply nanosecond clock accuracy.

Throughput includes the driver's post-receipt fee/balance checks before the next arrival; it is drained sequential completion throughput. The one-inflight sender design and memory-harness history copies intentionally trade performance for simple nonce/recovery semantics. Do not extrapolate these numbers to real network throughput or claim database scalability from them.

## Reproduce and inspect

Run `npm.cmd run benchmark:mvp2` from the configured pinned runtime; no Supabase or public RPC is used. It creates a new run directory and keeps completed raw rows plus an incomplete marker on failure. A successful run exits zero only after receipt/event/balance checks for all six workloads. Use `node scripts/verify-gasless-benchmark.mjs <run-directory>` to recompute source/raw/logical checksums, gas/fee totals, counts and payer attribution offline. The source snapshot is retained because no new Git commit was authorized.

Repeat on an isolated host, use a reviewed live Supabase project and an approved immutable source revision, then separately measure public-network confirmation/finality and real MetaMask interactions before making broader thesis claims. See [measurement contract](measurement-spec.md).
